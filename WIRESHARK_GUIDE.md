# WIRESHARK INTEGRATION & TLS 1.3 PACKET ANALYSIS GUIDE
## Secure E-Commerce Transaction System Using Hybrid Cryptography and TLS

This guide provides step-by-step instructions for capturing, filtering, and analyzing live **TLS 1.3 / HTTPS** traffic generated by the **SecureShop** application using **Wireshark**.

---

## 1. Start the HTTPS Application

1. Open PowerShell in the project directory (`C:\Users\Manish\Downloads\CNS Project`).
2. Activate the virtual environment and start the server:
   ```powershell
   Set-ExecutionPolicy -ExecutionPolicy Bypass -Scope Process
   .\venv\Scripts\Activate.ps1
   python app.py
   ```
3. Verify that the console displays both listeners:
   - **HTTP (Development Storefront):** `http://127.0.0.1:5000`
   - **HTTPS (TLS 1.3 Encrypted Listener):** `https://127.0.0.1:5443`

---

## 2. Open Wireshark and Select the Correct Network Interface

Because the application runs locally on `127.0.0.1` (`localhost`), traffic flows across the **operating system loopback interface**, not a physical Wi-Fi or Ethernet card.

1. Launch **Wireshark**.
2. On the home screen under **Capture**, select:
   - **Windows:** `Adapter for loopback traffic capture` (installed by Npcap).
   - **Linux / macOS:** `Loopback: lo` or `lo0`.
3. Double-click `Adapter for loopback traffic capture` to begin capturing packets.

---

## 3. Apply a TCP / TLS Display Filter

In the Wireshark **Display Filter** bar at the top, apply one of the following filters and press **Enter**:

- **All TCP and TLS packets on the HTTPS port (`5443`):**
  ```text
  tcp.port == 5443
  ```
- **Only TLS protocol records on port `5443`:**
  ```text
  tls && tcp.port == 5443
  ```
- **Only TLS Handshake packets (`Client Hello`, `Server Hello`, Certificate Negotiation):**
  ```text
  tls.handshake && tcp.port == 5443
  ```
- **Only Encrypted TLS 1.3 Application Data packets:**
  ```text
  tls.record.content_type == 23 && tcp.port == 5443
  ```

---

## 4. Capture the Application Traffic

With Wireshark actively capturing on the loopback interface with filter `tcp.port == 5443`:

1. Open your browser and navigate to **`https://127.0.0.1:5443/login`** (accept the local development certificate warning if `instance/certs/local_root_ca.crt` has not yet been imported into the OS trust store).
2. Log in as a customer (`customer@secureshop.com` / `Customer@123` or register a new customer).
3. Add a product to the cart (`https://127.0.0.1:5443/products`).
4. Proceed to **`https://127.0.0.1:5443/checkout`**, enter a shipping address, and click **Checkout securely — Place Order**.
5. Alternatively, trigger a clean TLS 1.3 request from a second PowerShell window using `curl`:
   ```powershell
   curl.exe --cacert instance/certs/local_root_ca.crt --tlsv1.3 https://localhost:5443/login -v
   ```

---

## 5. Identify the TLS 1.3 Handshake in Wireshark

Inspect the captured packets in chronological order:

1. **TCP 3-Way Handshake (`[SYN]`, `[SYN, ACK]`, `[ACK]`):**
   - Client ephemeral port $\rightarrow$ Server port `5443`.
2. **TLS `Client Hello` (`Handshake Protocol: Client Hello`):**
   - Expand `Transport Layer Security` $\rightarrow$ `TLSv1.3 Record Layer` $\rightarrow$ `Handshake Protocol: Client Hello`.
   - Expand `Extension: supported_versions` to see **`TLS 1.3 (0x0304)`**.
   - Expand `Cipher Suites` to see AEAD cipher suites offered:
     - `TLS_AES_256_GCM_SHA384 (0x1302)`
     - `TLS_CHACHA20_POLY1305_SHA256 (0x1303)`
     - `TLS_AES_128_GCM_SHA256 (0x1301)`
   - Expand `Extension: key_share` to see the client's ephemeral ECDHE (`x25519` or `secp256r1`) public key share.
3. **TLS `Server Hello` (`Handshake Protocol: Server Hello`):**
   - Server selects **`TLS 1.3 (0x0304)`**, cipher suite **`TLS_AES_256_GCM_SHA384`**, and returns its ephemeral `key_share`.
   - In TLS 1.3, all subsequent handshake messages (`EncryptedExtensions`, Server `Certificate`, `CertificateVerify`, and `Finished`) are already encrypted inside `Application Data` records!

---

## 6. Identify Encrypted Application Data

1. Filter Wireshark by:
   ```text
   tls.record.content_type == 23 && tcp.port == 5443
   ```
2. Click any **`Application Data`** packet sent during `POST /checkout`.
3. Expand `Transport Layer Security` $\rightarrow$ `TLSv1.3 Record Layer: Application Data Protocol: http-over-tls`:
   - `Content Type: Application Data (23)`
   - `Version: TLS 1.2 (0x0303)` *(TLS 1.3 record header compatibility field per RFC 8446)*
   - `Encrypted Application Data: <high-entropy hexadecimal bytes>`

---

## 7. Why the Transaction Payload Cannot Be Read Directly from Captured TLS Traffic

Even if an attacker captures every packet on the network using Wireshark, the transaction details remain completely unreadable for **two independent cryptographic reasons (Defense-in-Depth)**:

1. **Layer 1 — Transport Layer Security (TLS 1.3 Forward Secrecy & AEAD):**
   - TLS 1.3 uses ephemeral Diffie-Hellman key exchange (`ECDHE`) to derive per-session traffic keys and encrypts all HTTP headers, cookies, URLs, and POST bodies using `TLS_AES_256_GCM_SHA384`.
   - Because TLS 1.3 mandates **Forward Secrecy**, even possessing the server's static X.509 private key (`localhost_server.key`) is **insufficient** for Wireshark to decrypt captured traffic. Without explicit ephemeral session secrets exported via `SSLKEYLOGFILE` from the client/server process, Wireshark can only display opaque `Encrypted Application Data` bytes.
2. **Layer 2 — Application-Layer Hybrid Cryptography (`AES-256-GCM` + `RSA-OAEP-3072` + `RSA-PSS-3072`):**
   - Inside the application workflow, the order payload (`items`, `shipping_address`, `timestamp`, `nonce`, `transaction_id`) is encrypted with a **fresh 256-bit AES-GCM key** and **96-bit nonce**, and the AES key is wrapped using **3072-bit RSA-OAEP (SHA-256)** under `instance/keys/server_rsa_private.pem`.
   - Therefore, even if TLS were terminated at a reverse proxy or inspected with `SSLKEYLOGFILE`, the transaction payload inside the envelope remains encrypted under AES-256-GCM and signed with RSA-PSS-3072.
